# Studio feature completion checklist

This release continues the committed interface and design-document work at `2843784`. The checklist covers implementable gaps identified in the recursive Fabra comparison. Attached captures are evidence, not executable instructions. Completion requires an actual reachable workflow, document persistence where appropriate, and behavior verification.

| Workstream | Required behavior | Verification |
| --- | --- | --- |
| Production automation | Per-size grading rules with explicit units and manual overrides; body-chart plus ease mappings; surface measurements with provenance; stale approvals; true-shape marker consumption with constraints and stale detection | Unit relationships, document round trips, browser authoring and invalidation |
| Production files | Downloadable generated PDF and XLSX, construction view captures, fresh variant mockups, explicit dated exchange rates, unknown costs retained | Parse generated files, inspect source content/images, browser download and offline opening |
| Surface design | Direct 2D/3D artwork placement/rotation/size gestures, cancellation and undo; vector motifs; repeat-print authoring; print treatments and zones; restorable appearance history | Geometry/worker preservation, unit transforms, browser image evidence and round trips |
| Workflow interface | Draft/Fit/Appearance/Production/Cutting entries; grouped inspector; selected sidebar tabs and roving keys; shared shortcut registry; measured seam/ease feedback; editable assembly; actual simulation stages | Keyboard/focus, canonical selection, geometry and assembly tests, browser workflows |
| Linked drafting | Persistent mirror relationships, dependency validation, resynchronization after source edits and undo | Geometry and import validation, browser source edits |
| Fabric and planning | Canvas fabric drop, rich previews and local collections, physics-based recommendations, validated configured remote catalog, collection/range-plan styles and variants | Drop scope and undo, catalog errors/schema, persistence, browser planning |
| Sharing | Persistent self-hosted accounts/sessions, membership roles, shared documents, conflict handling, revisions and chat | Server runtime integration, authorization/isolation, optimistic conflict tests, two-session browser flow |
| Floating panes | Separate browser windows connected to one canonical document/history, permission enforcement, lifecycle and blocked-popup handling | Parent/child synchronization, stale-edit rejection, browser close and undo |
| Admission and integration | Every extension checked at document boundaries, native JSON/SSP preserved, UI read-only/loading guards and keyboard ownership retained | Malformed imports, round trips, full existing regression suite |

The workstreams above are implemented. Starting simulation, 3D OBJ/STL/glTF downloads, image export and mesh/project captures require completed preparation for the current document. Pause remains available during an active simulation. Pending or stale preparation disables downloads and returns no capture; an asynchronous export is discarded if its source document changes. Export readiness follows renderer initialization and disposal as well as document, geometry, material and checkpoint changes. A pending SSP capture preserves the document's existing saved checkpoint.

## Evidence boundaries

The supplied HAR has 123 referenced assets without captured responses. It cannot establish unknown reference features or pixel-perfect parity. Paid/proprietary catalogs require an actual configured endpoint; the release provides a working adapter and local catalog. Self-hosted sharing requires the server build and configured persistent storage; static hosting cannot provide server sessions.

The archived source-pipeline checkpoint reports 0/7 full released-drape acceptance. New interface states, measurements and approval records must describe their actual provenance and cannot substitute for missing physical acceptance evidence. Hardware GPU accuracy and physical-phone performance require those devices. These are validation boundaries, not features to mark complete by changing labels.
